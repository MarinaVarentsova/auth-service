==================================================
1. BODY LIMIT — ДОВЕСТИ ДО КОНЦА
==================================================

Для:

POST /api/auth/login
POST /api/auth/register
POST /api/auth/forgot-password

максимальный ФАКТИЧЕСКИЙ размер request body = 64 KB.

Content-Length оставить только как быстрый первый guard.

Обязательно:

- прочитать raw body;
- проверить реальный UTF-8 byte size через
  Buffer.byteLength(rawBody, "utf8");
- если >64 KB → сразу HTTP 413;
- только после проверки выполнять JSON.parse(rawBody).

Нельзя полагаться только на Content-Length.
Нельзя использовать req.json() до фактической проверки размера.

Ответ 413:

{
  "success": false,
  "error": "Размер запроса превышает допустимый."
}

Malformed JSON должен давать корректный клиентский 400,
а не 500.

2. LOGIN IP LIMIT
==================================================

Оставить:

5 запросов / 10 минут / client IP.

Проверять максимально рано до:

- JWT.

При превышении:

HTTP 429

Header:

3. LOGIN EMAIL PROTECTION
==================================================

Текущую реализацию,
где 5 ЛЮБЫХ запросов на email блокируют владельца,
НЕ оставлять.

Использовать:

10 НЕУСПЕШНЫХ login attempts
/ 10 минут
/ normalized email.

Email:

trim().toLowerCase()

Успешный login:
- НЕ считается неуспешной попыткой;
- сбрасывает failed-attempt counter этого email.

Неуспешная авторизация:
- увеличивает failed-attempt counter.

При достижении лимита:
→ HTTP 429 с тем же пользовательским security message.

Не менять существующий обычный ответ
при неправильном логине/пароле.

Не раскрывать существование email.

==================================================
6. CLIENT IP
==================================================

Auth находится за одним reverse-proxy hop Coolify/Traefik.

Не использовать доверчивую схему:

x-real-ip
→ первый X-Forwarded-For

если эти значения могут быть подделаны клиентом.

Реализовать определение IP для одного trusted proxy hop так,
чтобы простая отправка клиентом:

X-Forwarded-For: fake-ip

не позволяла менять rate-limit key.

Для X-Forwarded-For использовать адрес,
добавленный ближайшим доверенным reverse proxy,
а не первый пользовательский адрес цепочки.

Не менять Coolify config.

Не добавлять внешний сервис.
