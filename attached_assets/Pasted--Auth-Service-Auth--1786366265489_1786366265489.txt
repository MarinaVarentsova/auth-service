НЕ менять БД.

НЕ менять rate limiting.
НЕ менять consent.

==================================================
1. ОГРАНИЧЕНИЯ
==================================================

Использовать:

email:
максимум 254 символа

password:
максимум 128 символов

full_name:
максимум 200 символов

phone:
максимум 32 символа

project_code:
максимум 100 символов

Применять только там,
где соответствующее поле реально используется.


==================================================
2. LOGIN
==================================================

POST /api/auth/login

Проверять до:
- DB lookup;
- bcrypt;
- JWT.

email >254
или
password >128
или
project_code >100

→ HTTP 400

{
  "success": false,
  "error": "Некорректные данные запроса."
}

Не раскрывать,
какое именно поле превысило security limit.


==================================================
3. REGISTER
==================================================

POST /api/auth/register

Проверять после parse body,
но ДО:
- bcrypt;
- transaction;
- DB;
- consent create;
- verification email.

Ограничения:

email <=254
password <=128
full_name <=200
phone <=32
project_code <=100

Если optional phone отсутствует/null:
это валидно как раньше.

При превышении:

HTTP 400

{
  "success": false,
  "error": "Некорректные данные запроса."
}

Не менять существующие требования:
- обязательность полей;
- consent_personal_data;
- consent_platform_rules;
- consent_marketing optional;
- password rules;
- duplicate email;
- transaction.


==================================================
4. FORGOT PASSWORD
==================================================

POST /api/auth/forgot-password

email <=254

project_code <=100, если используется.

Проверять до DB/email отправки.

При превышении:
400 + безопасный текст.


==================================================
5. НЕ МЕНЯТЬ PASSWORD POLICY
==================================================

max length 128 — это только верхняя граница.

Не менять:
- минимальную длину;
- требования к символам;
- hashing;
- bcrypt rounds;
- существующие validation messages,
кроме нового overflow case.


==================================================
6. NORMALIZATION
==================================================

Существующую нормализацию email сохранить.

Не обрезать длинное значение автоматически.

Если длина превышена:
отклонить запрос.

Не делать substring/truncate.
