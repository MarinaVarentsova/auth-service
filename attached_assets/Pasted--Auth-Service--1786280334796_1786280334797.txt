Работаем ТОЛЬКО в Auth Service.

Исправляем ОДНУ проблему безопасности:
отсутствие защиты от массовых запросов / brute force / email flood.

Это production security fix.

КРИТИЧЕСКИ ВАЖНО:
- не проводить новый общий аудит;
- не менять архитектуру Auth Service;
- не менять БД;
- не менять Prisma;
- не менять JWT;
- не менять AUTH_SECRET;
- не менять бизнес-логику login/register/verify/reset;
- не менять успешные API responses;
- не менять email templates;
- не добавлять Redis;
- не добавлять внешний сервис;
- не менять Coolify;
- не делать commit;
- не делать push;
- не делать deploy.

Сервер имеет ограниченные ресурсы.

Реализация rate limiter сама НЕ должна создавать риск заполнения RAM или диска.


==================================================
1. СНАЧАЛА НАЙТИ ФАКТИЧЕСКИЕ ENDPOINTS
==================================================

Определи реальные существующие routes для:

- login;
- register;
- forgot password;
- resend verification.

Если какого-то endpoint нет:
НЕ создавать его.
Просто указать это в отчёте.

Не менять названия существующих endpoints.


==================================================
2. LOGIN — ЗАЩИТА ОТ ПЕРЕБОРА ПАРОЛЕЙ
==================================================

Для POST login установить одновременно два ограничения:

A. максимум 5 запросов / 10 минут / IP;

B. максимум 5 запросов / 10 минут /
нормализованный email.

Нормализация email:

trim().toLowerCase()

Если превышен ХОТЯ БЫ один из лимитов:
запрос блокируется.

ВАЖНО:

Rate limit должен проверяться максимально рано,
ДО дорогих операций:

- bcrypt/password verification;
- JWT signing;
- лишних DB queries, насколько это возможно без изменения текущей логики.

Цель:
заблокированный запрос должен потреблять минимум CPU, RAM и PostgreSQL ресурсов.


==================================================
3. REGISTER
==================================================

Для POST register:

максимум 3 запроса / 60 минут / IP.

После достижения лимита НЕ выполнять:

- hashing пароля;
- поиск/создание пользователя;
- создание auth_users;
- запись auth_consents;
- verification token;
- отправку verification email;
- другие операции регистрации.

Нормальная регистрация в пределах лимита должна работать абсолютно как сейчас.


==================================================
4. FORGOT PASSWORD
==================================================

Если такой endpoint существует:

IP:
максимум 3 запроса / 60 минут.

EMAIL:
максимум 2 запроса / 30 минут
на один нормализованный email.

Использовать оба ограничения одновременно.

После срабатывания limiter:

- НЕ отправлять UniSender email;
- НЕ создавать новые reset tokens;
- НЕ выполнять лишние DB операции.


==================================================
5. RESEND VERIFICATION
==================================================

Если такой endpoint существует:

IP:
максимум 3 запроса / 60 минут.

EMAIL:
максимум 2 запроса / 30 минут
на один нормализованный email.

После срабатывания limiter:

- НЕ отправлять verification email;
- НЕ создавать новый token;
- НЕ выполнять лишнюю DB/business логику.


==================================================
6. ПОНЯТНОЕ СООБЩЕНИЕ ПОЛЬЗОВАТЕЛЮ
==================================================

При срабатывании любого rate limit пользователь НЕ должен видеть:

- "rate limit";
- "Too Many Requests";
- IP;
- email;
- количество выполненных попыток;
- название limiter;
- технические детали;
- stack trace.

Использовать единый пользовательский текст:

"Мы заботимся о безопасности пользователей, поэтому подключения временно ограничены. Попробуйте снова через X минут."

X обязательно рассчитывать из ФАКТИЧЕСКОГО оставшегося времени блокировки.

Пример:

если осталось 8 минут:

"Мы заботимся о безопасности пользователей, поэтому подключения временно ограничены. Попробуйте снова через 8 минут."

Если осталось менее 60 секунд:

показывать:

"Мы заботимся о безопасности пользователей, поэтому подключения временно ограничены. Попробуйте снова через 1 минуту."

Никогда не показывать:
"через 0 минут".


==================================================
7. API RESPONSE ПРИ БЛОКИРОВКЕ
==================================================

HTTP status:

429 Too Many Requests

JSON:

{
  "success": false,
  "error": "Мы заботимся о безопасности пользователей, поэтому подключения временно ограничены. Попробуйте снова через X минут.",
  "retry_after_seconds": N
}

где:

N = фактическое число секунд до разблокировки.

Также вернуть HTTP header:

Retry-After: N

Не изменять формат успешных responses.


==================================================
8. FRONTEND MESSAGE
==================================================

Проверить только текущий Auth Service:

может ли его frontend показать поле `error` из API response.

Если frontend Auth Service показывает API error —
обеспечить, чтобы пользователь видел именно сообщение:

"Мы заботимся о безопасности пользователей, поэтому подключения временно ограничены. Попробуйте снова через X минут."

Если основной frontend регистрации находится в ДРУГОМ проекте Палаты:

НЕ менять другой проект.

В отчёте написать:

FRONTEND_429_MESSAGE_SUPPORT_REQUIRED = YES

и указать, какой response уже будет возвращать Auth Service,
чтобы frontend Палаты потом просто показал поле error.


==================================================
9. НЕ РАСКРЫВАТЬ ПРИЧИНУ БЛОКИРОВКИ
==================================================

Пользователь не должен понимать:

- IP-limit это был или email-limit;
- сколько запросов сделано;
- какой threshold;
- какое значение IP используется;
- какое email значение является ключом.

Rate limiter — внутренний защитный механизм.


==================================================
10. ОГРАНИЧЕНИЕ RAM
==================================================

Если используется in-memory limiter:

ЗАПРЕЩЕНО создавать бесконечно растущий Map/Object/cache.

Обязательно реализовать:

- TTL каждой записи;
- автоматическое удаление истёкших записей;
- периодический cleanup;
- hard cap общего числа активных limiter keys.

Максимум:

10 000 активных limiter keys
НА ВЕСЬ Auth Service.

Если hard cap достигнут:

1. сначала удалить expired entries;
2. затем удалить самые старые записи;
3. НЕ увеличивать хранилище бесконечно.

Не использовать PostgreSQL для limiter.

Не создавать новую таблицу.

Не создавать Redis.

Cleanup timer не должен удерживать Node process при shutdown,
если runtime позволяет корректно вызвать unref().


==================================================
11. НЕ ЗАБИВАТЬ ДИСК ЛОГАМИ
==================================================

Rate limiting НЕ должен генерировать лог на каждый заблокированный запрос.

При атаке в 100 000 запросов мы не должны получить 100 000 строк логов.

Допустимо:

- логировать только первое срабатывание для key/window;
или
- делать throttled/aggregated logging.

Лог может содержать:

[AUTH_RATE_LIMIT] endpoint=login

НЕ логировать:

- password;
- token;
- полный email;
- request body;
- AUTH_SECRET;
- API keys;
- полный IP + email вместе.

Цель:
защита от атаки не должна сама заполнить диск.


==================================================
12. BODY SIZE PROTECTION
==================================================

Проверить текущий максимальный размер request body
для публичных Auth endpoints.

Если разумного ограничения нет:

установить максимум 64 KB для:

- login;
- register;
- forgot password;
- resend verification.

Этим endpoints не нужен megabyte-sized JSON.

При превышении:

HTTP 413 Payload Too Large

JSON:

{
  "success": false,
  "error": "Размер запроса превышает допустимый."
}

Не возвращать stack trace.

Не менять ограничения других endpoints без необходимости.


==================================================
13. CLIENT IP ЗА COOLIFY
==================================================

Auth Service работает за Coolify / reverse proxy.

Нужно корректно определить client IP.

НЕ доверять слепо первому значению произвольного:

X-Forwarded-For

если пользователь может его подделать.

Проверить текущую Next.js/Coolify архитектуру
и выбрать минимально корректный источник IP.

Не менять конфигурацию Coolify в этой задаче.

В отчёте указать:

CLIENT_IP_SOURCE = ...

и кратко объяснить,
почему это значение считается корректным в текущей архитектуре.


==================================================
14. НЕ ЗАБЛОКИРОВАТЬ НОРМАЛЬНУЮ РАБОТУ ПАЛАТЫ
==================================================

НЕ устанавливать глобальный limiter на весь Auth Service.

НЕ ограничивать этим изменением:

- GET /me;
- logout;
- verify token;
- health;
- внутренние authenticated обращения Палаты;
- другие обычные authenticated endpoints.

Ограничить только публичные потенциально опасные endpoints:

login
register
forgot password
resend verification.

15. НА ЧТО ВЛИЯЕТ КАЖДОЕ ОГРАНИЧЕНИЕ
==================================================

В итоговом отчёте отдельно написать бизнесовым языком:

LOGIN IP LIMIT
→ какую атаку останавливает;
→ какие ресурсы сервера защищает.

LOGIN EMAIL LIMIT
→ зачем нужен одновременно с IP limit;
→ что защищает.

REGISTER LIMIT
→ как защищает от массового создания аккаунтов;
→ как защищает БД, CPU и отправку писем.

FORGOT PASSWORD LIMIT
→ как защищает от email flood;
→ как защищает UniSender и БД.

RESEND VERIFICATION LIMIT
→ как защищает пользователя от почтового спама;
→ как защищает UniSender.

BODY LIMIT
→ как защищает RAM/Node process.

MEMORY HARD CAP
→ как предотвращает ситуацию,
когда сам limiter начинает съедать память.

LOG THROTTLING
→ как защищает ограниченное дисковое пространство сервера.

17. ТЕСТЫ
==================================================

НЕ выполнять реальный load/DDoS test.

Использовать unit/mock/local последовательные запросы.

Проверить:

LOGIN:

1–5 запросов в окне:
→ проходят в существующую login-логику.

6-й:
→ HTTP 429.

Проверить:

retry_after_seconds > 0.

Retry-After header присутствует.

Текст содержит фактическое время ожидания.

REGISTER:

1–3:
→ обычная логика.

4-й:
→ HTTP 429.

После 429:

hashing/user creation/consent/email не выполняются.

FORGOT PASSWORD:

если endpoint есть:
проверить IP limiter;
проверить email limiter;
после блокировки email не отправляется.

RESEND:

аналогично.

BODY:

request > 64 KB
→ HTTP 413.

MEMORY:

- expired entries удаляются;
- hard cap = 10 000;
- storage не растёт бесконечно.

WINDOW EXPIRY:

после окончания периода блокировки
следующий запрос снова разрешается.

Запустить:

npm run build

typecheck / tsc, если предусмотрен

существующие tests.
