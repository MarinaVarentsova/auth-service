2. НЕ ВНЕДРЯТЬ НОВУЮ REFRESH-АРХИТЕКТУРУ
==================================================

Если фактически refresh token в системе НЕ существует:

НЕ создавать его.

НЕ добавлять:
- refresh token generation;
- refresh token DB storage;
- cookies;
- session table;
- rotation;
- revocation list;
- Redis.

Вместо этого убрать ложное ощущение,
что refresh механизм работает.


==================================================
3. /refresh — FAIL CLOSED
==================================================

Если текущий /refresh является заглушкой
или не имеет реального refresh token:

он НЕ должен выдавать новый access token
и НЕ должен делать вид, что refresh поддерживается.

Вернуть контролируемый ответ:

HTTP 401

{
  "success": false,
  "error": "Сессия истекла. Пожалуйста, войдите снова."
}

Не раскрывать технические детали.

Не менять access token.


==================================================
4. /logout
==================================================

Если server-side session storage сейчас отсутствует:

не создавать новую инфраструктуру только ради logout.

Logout должен:

- корректно завершать текущий client session flow;
- не выдавать новый token;
- не обновлять access token;
- не создавать refresh token;
- возвращать безопасный success response.

Например:

HTTP 200

{
  "success": true
}

Frontend после logout должен удалить текущий access token
из своего существующего storage.

Не менять UI.


==================================================
5. FRONTEND
==================================================

Проверить текущий logout flow.

После успешного logout:

- access token удалён;
- user state очищен;
- пользователь возвращается в существующий login flow;
- защищённые страницы больше не доступны через frontend state.

Если frontend сейчас вызывает /refresh автоматически:

убрать зависимость от fake refresh endpoint.

При 401 от защищённого API:
использовать существующий logout/login flow,
а не пытаться бесконечно refresh-ить сессию.

НЕ менять внешний UX.


==================================================
6. ACCESS TOKEN TTL
==================================================

Проверить текущий фактический access token TTL.

НЕ менять его.

В отчёте указать точное текущее значение.

После logout старый access token,
если он был скопирован отдельно,
может технически жить только до окончания своего текущего TTL.

Это принимается как текущая архитектурная модель.

Не создавать blacklist access tokens.


==================================================
7. НЕ СОЗДАВАТЬ ЛОЖНУЮ SERVER-SIDE INVALIDATION
==================================================

Не утверждать,
что access token мгновенно инвалидируется server-side,
если blacklist/session store отсутствуют.

Нужно честно сохранить модель:

logout
→ client token удалён

access token
→ сам истекает по TTL

refresh
→ новый token не выдаётся.
