Работаем ТОЛЬКО в Auth Service.

Исправляем ОДНУ security-проблему:

User enumeration через POST /api/auth/login.

Сейчас внешние ответы позволяют отличить:
- email не существует;
- email существует, но не подтверждён;
- другие причины отказа.

Из-за этого посторонний может проверять,
зарегистрирован ли конкретный email.

ЦЕЛЬ:

сохранить текущую бизнес-логику login,
но сделать внешние ответы такими,
чтобы по ним нельзя было определить существование аккаунта.

ВАЖНО:

НЕ проводить новый аудит.
НЕ менять register.
НЕ менять verify.
НЕ менять reset-password.
НЕ менять forgot-password.
НЕ менять JWT.
НЕ менять AUTH_SECRET.
НЕ менять БД.
НЕ менять Prisma.
НЕ менять rate limiting.
НЕ менять password hashing.
НЕ менять успешный login response.
НЕ менять frontend без необходимости.
НЕ делать commit/push/deploy.


==================================================
1. НАЙТИ ТЕКУЩИЕ ВЕТКИ LOGIN
==================================================

Найти POST /api/auth/login
и все ветки отказа, связанные с:

- user/email не найден;
- неправильный пароль;
- email не подтверждён;
- project_code / project mismatch;
- другие auth failures.

После этого сразу исправить внешний response.


==================================================
2. УНИФИЦИРОВАТЬ ПУБЛИЧНЫЕ ОТВЕТЫ
==================================================

Для случаев:

- email не существует;
- пароль неверный;
- email существует, но пользователь не может пройти login;
- другие случаи, которые сейчас позволяют определить наличие аккаунта,

публичный HTTP response должен быть одинаковым,
если нет отдельной продуктовой необходимости показать пользователю
специальный безопасный статус.

Предпочтительный единый ответ:

HTTP 401

{
  "success": false,
  "error": "Неверный email или пароль."
}

Не возвращать наружу:

- "пользователь не найден";
- "email существует";
- "email не подтверждён";
- user id;
- project id;
- внутренний auth status;
- DB details.


==================================================
3. НЕ СЛОМАТЬ EMAIL VERIFICATION UX
==================================================

КРИТИЧЕСКИ:

если frontend реально использует отдельный статус
"email не подтверждён"
для полезного пользовательского сценария,
например чтобы показать кнопку повторной отправки письма,

НЕ ломать этот flow автоматически.

В этом случае найти минимальный безопасный вариант,
при котором внешний response всё равно
не позволяет достоверно определить существование email.

Например:
не использовать различающиеся HTTP status/body
для enumeration-safe login response.

Не придумывать новый UX.
Сохранить существующий пользовательский сценарий максимально близко.


==================================================
4. RATE LIMIT НЕ МЕНЯТЬ
==================================================

Существующие login rate limits оставить без изменений.

Не менять:

5 req / 10 min / IP
failed-email limiter
Retry-After
429 message.


==================================================
5. SERVER LOGS
==================================================

Backend может различать внутренние причины отказа
для диагностики.

Но не логировать:

- password;
- token;
- AUTH_SECRET;
- полный request body.

Не добавлять новые подробные логи.


==================================================
6. SUCCESS LOGIN НЕ МЕНЯТЬ
==================================================

При корректном email/password/статусе пользователя:

успешный login должен работать абсолютно как сейчас.

Не менять:

- token payload;
- token TTL;
- response schema;
- user fields;
- /me compatibility.


==================================================
7. ПРОВЕРКИ
==================================================

Проверить:

A.
несуществующий email
→ безопасный внешний ответ.

B.
существующий email + неправильный пароль
→ ТОЧНО такой же внешний status/body.

C.
существующий неподтверждённый пользователь
→ не раскрывает факт существования аккаунта
в сравнении с несуществующим email.

D.
валидный подтверждённый пользователь
→ login PASS.

E.
rate limit продолжает работать.

F.
frontend login flow не сломан.

G.
build/typecheck.

Если repository tests есть — запустить.
Если нет — написать NONE.
